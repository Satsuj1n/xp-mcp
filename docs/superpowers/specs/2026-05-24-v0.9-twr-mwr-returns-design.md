## 1. Why

The v0.6 spec deferred TWR / MWR computation explicitly:

> **TWR / MWR calculation tool** — the whole point of capturing cash flows,
> but a separate feature with its own design considerations (valuation
> snapshots, sub-period handling). Defer.

v0.7 shipped `suggest_buys`. v0.8 closed the `cash_flow_summary` debt.
v0.9 closes the TWR / MWR debt — the user now has cash flows (v0.6) and
valuation snapshots (via existing `imports` records) — enough raw data
to answer "how much did I earn?" both removing and including the effect
of contribution timing.

## 2. Scope

- **In:** two new MCP tools — `calculate_twr` and `calculate_mwr`.
- **In:** pure service `services/returns.ts` exporting `computeReturns`,
  `computeTwr`, `computeMwr` (plus helpers).
- **In:** new repo function `listValuationSnapshots(db, periodFrom?, periodTo?)`
  in `storage/imports-repo.ts`, querying `imports` table.
- **In:** README + version bump 0.8.0 → 0.9.0 + CI smoke (12 → 14 tools).

- **Out:** no schema change. Valuation snapshots are derived from
  existing `imports` rows where `source_type='pdf_xperformance' AND
  declared_total_cents IS NOT NULL AND reference_date IS NOT NULL`.
- **Out:** no daily NAV. The granularity is one snapshot per XPerformance
  import; we use **Modified Dietz** between consecutive snapshots and
  chain them geometrically. This is the GIPS approach for portfolios
  without daily valuation.
- **Out:** no benchmark comparison (CDI / IBOV). That's a separate
  feature requiring an external data source.
- **Out:** no per-asset return decomposition. TWR / MWR are portfolio-
  level only in v0.9. Per-asset returns require complete `transactions`
  data, which depends on the still-deferred `import_nota_corretagem_pdf`
  TODO.

## 3. Algorithms

### 3.1 TWR via Modified Dietz, chained geometrically

For each consecutive pair of snapshots `(S_i, S_{i+1})`, compute the
sub-period return:

```text
  V_start   = S_i.declared_total
  V_end     = S_{i+1}.declared_total
  CF_j      = signed cash flows in (S_i.date, S_{i+1}.date]
              (APORTE → positive, RESGATE → negative)
  net_CF    = sum(CF_j)

  w_j       = (period_days - days_since_start(CF_j)) / period_days
  weighted_CF = sum(CF_j * w_j)

  r_i = (V_end - V_start - net_CF) / (V_start + weighted_CF)
```

Chain: `TWR_period = ∏(1 + r_i) - 1`

**Why Modified Dietz** (and not true TWR):

- True TWR requires a valuation snapshot on the day of every cash flow.
  We do not have that data — snapshots come from manual XPerformance
  imports, not daily mark-to-market.
- Modified Dietz is the GIPS standard fallback for monthly / periodic
  valuation. CFP and CFA-curriculum acceptable.
- **Trade-off:** error grows when cash flows are large relative to the
  starting value of a sub-period. We emit warnings for risky cases
  (see § 6).

**Alternative descartada — true TWR with linear interpolation between
snapshots:** would require assuming linear NAV growth between snapshots
to estimate value at cash-flow date. That's a worse fiction than
Modified Dietz's assumption of uniform cash flow distribution. Not
chosen.

### 3.2 MWR via bisection IRR

The cash flow series for IRR is:

- For each cash flow CF_j: `(date_j, -amount_j_brl)` (outflow from
  investor → negative; APORTE is positive amount in DB → negated here
  because for the investor, an aporte is money leaving the wallet)
- Actually, by convention: APORTE means money INTO the portfolio
  (an inflow to the portfolio, an outflow from the investor's "external"
  wallet). MWR is the return ON the portfolio, so we frame cash flows
  from the **portfolio's** point of view:
  - `APORTE` → `+amount` (portfolio receives money)
  - `RESGATE` → `-amount` (portfolio gives money back)
- The portfolio starts at `V_first_snapshot` (initial inflow, equivalent
  to a synthetic APORTE on the first snapshot's date) and ends at
  `V_last_snapshot` (terminal outflow, equivalent to a synthetic
  RESGATE on the last snapshot's date — the "as if we sold today").

Wait — re-checking IRR convention. Standard textbook form:

```text
  NPV(r) = sum over j: CF_j / (1 + r)^t_j  = 0
```

where `CF_j` is signed from the **investor's** perspective. Investing
money is negative (money out of wallet). Receiving money back is
positive. So:

- `APORTE` → `-amount` (investor pays in)
- `RESGATE` → `+amount` (investor pulls out)
- Initial NAV at `period_from` → `-V_first` (synthetic initial investment)
- Terminal NAV at `period_to` → `+V_last` (synthetic final withdrawal)

The IRR `r` is the annualized rate that makes NPV zero. Solve via
**bisection** on `[-0.99, +10.0]` — bisection always converges if NPV
changes sign over the range. Tolerance: `|NPV| < 1e-6` (in BRL).
Max iterations: 100.

**Bisection > Newton:** Newton diverges easily for noisy IRR series.
Bisection is slightly slower (~30 iterations to converge for sane data)
but always converges within the bracket. For a personal portfolio with
~12-24 cash flows per year, both are fast enough.

**Convergence failure:** if NPV does not change sign over `[-0.99, 10]`,
or 100 iterations reach without `|NPV| < 1e-6`, return `converged:
false` and `mwr_period: null`. Surface to LLM client cleanly — don't
crash the tool.

### 3.3 Annualization

For both TWR and MWR:

```text
  annualized = (1 + r_period) ^ (365 / days) - 1
```

Where `days = (period_to - period_from)` in calendar days.

If `days < 30` → `annualized: null` (too short — annualizing a 5-day
return amplifies noise wildly). Period return still reported.

## 4. Input / output shapes

```ts
const calculateTwrSchema = z.object({

  period_to: z.string().regex(/^\d{4}-\d{2}-\d{2}$/).optional(),

export interface TwrResult {

  period_to: string;         // resolved (last snapshot if omitted)
  days: number;

  cash_flows_used: number;   // count of cash flow rows in window

    from: string;
    to: string;
    days: number;
    starting_value_brl: number;
    ending_value_brl: number;
    net_cash_flow_brl: number;
    period_return: number;
  }>;
  warnings: string[];
}
```

### 4.2 `calculate_mwr`

```ts
const calculateMwrSchema = z.object({

  period_to: z.string().regex(/^\d{4}-\d{2}-\d{2}$/).optional(),

export interface MwrResult {

  period_to: string;

  warnings: string[];

```

### 4.3 Shared error: insufficient history

If `listValuationSnapshots(db, ...)` returns < 2 rows, both tools fail
with a structured error message:

```text
  "Need at least 2 XPerformance imports to compute returns. Found N.
   Import another XPerformance PDF (or pass an earlier period_from /
   later period_to that covers ≥ 2 imports)."
```

Returned as an MCP tool error (not a thrown exception that crashes the
process). Existing handler pattern in `src/index.ts` wraps thrown
`Error`s into `isError: true` responses already — just throw with a
clear message.

## 5. Architecture

Mirrors v0.5/v0.7/v0.8 split:

```text
storage/imports-repo.ts
  + listValuationSnapshots(db, periodFrom?, periodTo?): SnapshotRow[]
    Returns imports rows where source_type='pdf_xperformance' AND
    declared_total_cents IS NOT NULL AND reference_date IS NOT NULL,
    optionally filtered by [periodFrom, periodTo], sorted by
    reference_date ASC. If two imports share the same reference_date,
    the latest imported_at wins (defensive — should be rare).

  + SnapshotRow type:
      { reference_date: string;       // YYYY-MM-DD
        declared_total_cents: number;
        import_id: number;
        imported_at: string; }

services/returns.ts                          (NEW)
  - computeTwr(snapshots, flows): TwrCore
  - computeMwr(snapshots, flows): MwrCore
  - computeReturns(snapshots, flows): { twr: TwrCore; mwr: MwrCore }
    The unified one — the tool wrappers project the half they need.
    Caller validates len(snapshots) >= 2 BEFORE calling.

tools/calculate-twr.ts                       (NEW)
  - Load snapshots in window via listValuationSnapshots
  - Load cash flows in window via listCashFlows + filters
  - Compute via computeTwr
  - Shape TwrResult

tools/calculate-mwr.ts                       (NEW)
  - Same load path
  - Compute via computeMwr
  - Shape MwrResult

src/index.ts
  + 2 new entries in TOOLS registry, with descriptions
```

The reason for the shared `computeReturns` even though the tools split:
when both are called (LLM client commonly does both), the service
computes everything once; the two wrappers project independently.

### 5.1 Sub-period assignment of cash flows

A cash flow with `flow_date == S_i.date` (matches a snapshot date) is
considered to occur AFTER the snapshot — it belongs to sub-period
`(S_i.date, S_{i+1}.date]`. Why: the snapshot reflects state at end of
day; same-day flows are interpreted as happening intraday.

A cash flow exactly on `period_to` is included in the last sub-period.

A cash flow exactly on `period_from` (the first snapshot date) is
**included** in the first sub-period (as a same-day flow after the
opening snapshot).

## 6. Warnings (quality signals, not blockers)

- **Sparse history:** if any sub-period spans > 60 days AND has ≥ 3
  cash flows → `"Sub-period {from} → {to} has {N} cash flows over {D}
  days; Modified Dietz precision degrades with sparse snapshots.
  Consider importing XPerformance more frequently."`
- **Large cash flow:** if any single cash flow's `|amount|` is > 30%
  of the sub-period's `starting_value` → `"Cash flow of R$ {X} on
  {date} is {P}% of sub-period starting value; Modified Dietz may
  overstate or understate the period return."`
- **Tiny period:** if `days < 30` → `"Period span is {N} days;
  annualized return omitted (statistically noisy)."`
- **Stale tail:** if `period_to` is implicit (defaults to last
  snapshot) AND latest snapshot is > 60 days old vs `new Date()` →
  `"Last snapshot is from {date}; latest portfolio state may be
  significantly different. Import a fresh XPerformance to refresh."`
- **MWR fallback:** if MWR did not converge → `"MWR bisection did not
  converge in the [-99%, 1000%] annualized range. Check for unusual
  cash flow patterns or report this as a bug."`
- **Filtered flows:** if any cash flows were loaded but excluded
  because they fall outside the snapshot window → `"{N} cash flows
  excluded — outside the snapshot window. Returns reflect only flows
  within [{period_from}, {period_to}]."`

## 7. Tests

### 7.1 `services/returns.test.ts` (pure unit, ~15-18 cases)

Canonical textbook cases:

- **TWR no cash flows:** 2 snapshots, V_start 1000, V_end 1100 →
  TWR = 10%, annualized depends on days.
- **TWR with single mid-period aporte:** the canonical CFA "Modified
  Dietz" example (hand-computable, ~5.2% type answer).
- **TWR geometric chain:** 3 snapshots → 2 sub-periods → assert
  chain equals `(1+r1)(1+r2)-1`.
- **TWR with resgate:** assert sign handling correct.
- **TWR same-day flow on snapshot:** flow on snapshot date goes into
  next sub-period.
- **MWR no cash flows:** 2 snapshots, V_start 1000, V_end 1100 → IRR
  matches expectation (period rate 10%, annualized depends on days).
- **MWR with single aporte:** hand-computable IRR.
- **MWR convergence on edge:** terminal at 0 (full loss) → IRR near
  -100%, but bisection bracket starts at -0.99 → may not converge or
  hit boundary; assert `converged: false` cleanly.
- **MWR convergence on extreme gain:** terminal 10× initial in 30
  days → annualized IRR enormous; bisection bracket caps at +10.0;
  assert behaviour.
- **Modified Dietz with large flow:** flow > 30% of start; assert
  computation still completes, warning triggers.
- **Days-since-start arithmetic:** carefully verify the
  `(period_days - days_since_start) / period_days` weighting matches
  textbook (one test that walks through the math).
- **Cross-year period:** snapshots spanning Dec → Jan, including a
  Christmas-time cash flow.
- **Period_to equals last snapshot:** verify same-day flow inclusion.
- **Period_from equals first snapshot:** verify same-day flow
  inclusion.
- **Annualization:** assert null when days < 30; correct formula
  otherwise.
- **Empty cash flows:** TWR reduces to simple geometric return;
  MWR reduces to `(V_last/V_first)^(365/days) - 1`.
- **2 snapshots same date:** edge case — should be deduped by the
  repo, but the service should also tolerate it (single sub-period of
  0 days → skip, no division by zero).
