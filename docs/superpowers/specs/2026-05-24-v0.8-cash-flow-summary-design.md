## 1. Why

The v0.6 spec (§ Out of scope, line 39) explicitly deferred surfacing
cash flow totals to a future iteration:

> Integration with `get_portfolio_summary` — possible future addition (e.g.,
> a `cash_flow_summary` block with YTD totals), but conceptually distinct
> (summary describes current state; cash flows are historical events). Defer
> to v0.7+.

v0.7 shipped `suggest_buys`. v0.8 closes that v0.6 debt — the user has
to call two tools (`get_portfolio_summary` + `get_cash_flows`) to see
current state and recent contribution rhythm side by side. The LLM
client can summarize both, but the panorama tool should be a
single-call panorama.

## 2. Scope

- **In:** new `cash_flow_summary` block in the `PortfolioSummary` return
  value with YTD (calendar year) + rolling 12-month aggregates.
- **In:** pure service `computeCashFlowSummary` (testable without DB).
- **In:** new repo function `listCashFlowsSince(db, dateFrom)` (unbounded
  list since a date — distinct from the paginated `listCashFlows`).
- **In:** empty-state handling (no cash flows → `null` + warning).
- **In:** README + smoke-test entry update + version bump 0.7.0 → 0.8.0.

- **Out:** no new tool — `cash_flow_summary` is just a new field on the
  existing summary output.
- **Out:** no schema change (uses existing `cash_flows` table from v0.6).
- **Out:** no TWR / MWR computation — that's the next iteration; cash
  flows here are descriptive (totals/averages), not return-bearing.
- **Out:** monthly per-month breakdown in the output — only aggregates.
  (`get_cash_flows` already serves the row-level query.)
- **Out:** customisable windows (YTD = calendar year, rolling = 12
  calendar months ending at `as_of_date`). Two decisions, not parameters.

## 3. Output shape

```ts
export interface CashFlowSummary {
  as_of_date: string;        // YYYY-MM-DD — derived from new Date()
  total_records: number;     // count of cash_flows rows used
  ytd: {
    year: number;            // calendar year of as_of_date
    aporte_brl: number;
    resgate_brl: number;
    net_brl: number;
  };
  rolling_12m: {
    from_month: string;      // "YYYY-MM" — 11 months before to_month
    to_month: string;        // "YYYY-MM" — month of as_of_date
    months_with_data: number;          // distinct months with ≥1 row, 0..12
    aporte_brl: number;
    resgate_brl: number;
    net_brl: number;
    monthly_avg_aporte_brl: number;    // aporte_brl / max(1, months_with_data)
    monthly_avg_net_brl: number;       // net_brl / max(1, months_with_data)
  };
}

// PortfolioSummary gains one field:
//   cash_flow_summary: CashFlowSummary | null;
```

### Why these choices

- **`as_of_date` independent of `computed_as_of`** — cash flows are
  historical events; the portfolio's last-imported-at timestamp would
  freeze the YTD window any time the user forgets to re-import an
  XPerformance PDF. The two clocks are decoupled.
- **YTD = calendar year, not rolling 365 days** — standard financial
  convention. Rolling 365d would also overlap with `rolling_12m` and
  duplicate information.
- **Average over `months_with_data`, not over 12 fixed months** — more
  honest. Penalising someone who started tracking 3 months ago with a
  "/12" denominator inflates the result's appearance of regularity.
  We expose `months_with_data` so the LLM can call out short history.
- **No per-month breakdown in the output** — keeps the panorama
  output bounded. Users wanting drill-down call `get_cash_flows`.

## 4. Edge cases

| Scenario | Behaviour |
|---|---|
| Zero cash flows in DB | `cash_flow_summary: null`; add warning `"No cash flows imported yet; cash_flow_summary unavailable"` |
| Cash flows exist but none in last 12 months | both `ytd` and `rolling_12m` totals are 0; `months_with_data: 0`; monthly averages are 0; `total_records` reflects the count of rows in the 12M window (which is 0 here — older rows are not loaded) |
| Cash flows exist but none YTD (e.g. January, no flows yet) | `ytd` totals all 0; `rolling_12m` reflects whatever is in the prior 12 months |
| Only APORTE rows in window | `resgate_brl: 0`; `net_brl == aporte_brl` |
| `as_of_date` mid-year | YTD window: `YYYY-01-01` ≤ `flow_date` ≤ `as_of_date`; rolling window: first day of (current month − 11 calendar months) ≤ `flow_date` ≤ `as_of_date` |

## 5. Architecture

Mirrors the v0.5/v0.7 split (pure service + thin tool wrapper):

```text
storage/cash-flows-repo.ts
  + listCashFlowsSince(db, dateFrom): CashFlowRow[]
    Unbounded list since a date, ordered by flow_date ASC (older first
    — easier for month-bucketing in the service).

services/cash-flow-summary.ts           (NEW)
  - computeCashFlowSummary(rows, asOfDate): CashFlowSummary
    Pure function. Takes pre-fetched rows + an ISO date; returns the
    summary. No DB, no time.

services/portfolio-summary.ts
  - computePortfolioSummary(positions, lastDecl, cashFlowSummary):
        PortfolioSummary
    Already accepts upstream-computed inputs. New optional
    `cashFlowSummary: CashFlowSummary | null` parameter — attached
    to the result; if null, warning emitted.

tools/get-portfolio-summary.ts
  - Compute the rolling-12m start date from `new Date()`
  - listCashFlowsSince(db, twelveMonthsStart)
  - computeCashFlowSummary(rows, asOfDate)
  - Pass into computePortfolioSummary
```

### Date arithmetic spec

`as_of_date = new Date()` formatted as `YYYY-MM-DD` (UTC).

- `ytd_start = "${year}-01-01"` where `year = parseInt(as_of_date.slice(0,4))`.
- `rolling_12m_from_month`: subtract 11 from current month index
  (month-1 because months are 1-based). If result < 1, wrap to prior
  year. Format `YYYY-MM`.
- `rolling_12m_start = "${from_month}-01"` — first day of `from_month`.
- `since = rolling_12m_start` — what's loaded from the DB.
- A row qualifies for the rolling window iff `flow_date ≥ rolling_12m_start`.
- A row qualifies for YTD iff `flow_date ≥ ytd_start AND flow_date ≤ as_of_date`.

`flow_date` strings compare lexicographically as ISO dates — no
`Date.parse` needed for the bucketing.

## 6. Reconciliation with existing tools

- `get_cash_flows` continues to be the row-level query. No change.
- `sumCashFlows` repo function is unchanged. We do **not** delegate to
  it — the pure service does its own aggregation over the loaded rows,
  to keep the service testable in isolation and to compute
  `months_with_data` (which the existing `sumCashFlows` cannot).

## 7. Tests

- `services/cash-flow-summary.test.ts` — pure service, ~12 cases:
  - happy path (mixed APORTE/RESGATE across multiple months)
  - empty rows → asserts caller responsibility (service returns
    zeroed summary; warning is added by caller)
  - all rows older than 12M (none qualify → 0/0 + months_with_data 0)
  - all rows YTD-only (rolling and YTD identical when YTD covers full
    rolling window — only true in late December)
  - single month with multiple rows → `months_with_data: 1`,
    average == that month's total
  - month-boundary: row dated `2025-06-01` with `as_of_date = 2026-05-31`
    qualifies (rolling window is `2025-06-01 .. 2026-05-31`)
  - month-boundary: row dated `2025-05-31` with same `as_of_date`
    excluded (one day before window)
  - January `as_of_date` — `ytd` has 0 days of history if `as_of_date` is
    `YYYY-01-01`; covers the early-year case
  - cross-year rolling window (Dec/Jan boundary)
  - resgate-only month → `aporte_brl: 0`, `net_brl` negative
  - rounding: cents inputs → BRL with 2 decimals
  - large numbers (R$ 1M+ aporte) — assert no float drift

- `storage/cash-flows-repo.test.ts` — extend with 3 cases for
  `listCashFlowsSince`:
  - returns rows with `flow_date >= dateFrom` only
  - sorted by `flow_date ASC, id ASC`
  - empty DB returns `[]`

- `tools/get-portfolio-summary.test.ts` — extend with 3 integration cases:
  - empty cash_flows table → `cash_flow_summary: null` + warning present
  - cash flows present → `cash_flow_summary` populated correctly (seed
    a known set, assert YTD totals)
  - existing tests still pass (no field breakage)

CI smoke whitelist nominal entries bumped 12 → 12 (no new tool, no
change). Smoke just needs to assert the new field is present in the
shape returned by `get_portfolio_summary`.

## 9. Migration / compatibility

- Output is **additive**: existing consumers ignoring unknown fields
  continue to work. `cash_flow_summary` is a new optional field with
  `null` as a valid state.
- No schema migration. Existing `cash_flows` table (v3 schema, v0.6)
  is the source.
- No new dependencies.
