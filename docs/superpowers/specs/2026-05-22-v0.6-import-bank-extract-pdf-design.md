## 1. Problem statement

`portfolio-mcp` through v0.5 ships nine MCP tools focused on the **current state** of the portfolio (positions, allocation drift, summary) and the **investment universe** (market data, screening). What it does not have is any concept of **historical capital flow**: the user cannot ask *"how much did I transfer into the brokerage account in the last 6 months?"* or *"what's my net contribution vs withdrawal since January?"*. Without that data, future features like time-weighted return (TWR) and money-weighted return (MWR) cannot exist — both require knowing when capital entered or left the investment account.

The XP brokerage exposes capital flow data through the **Conta Digital Extrato PDF** (the digital current-account statement), which lists every Pix, TED, bill payment, and — critically — **transfers between the digital account and the investment account**. Those investment transfers are exactly the APORTE (deposit) and RESGATE (withdrawal) signals we need.

The original TODO was written assuming a hypothetical "extrato" PDF that would contain trades and dividends. Inspection of an actual XP PDF revealed that document does not exist as named — XP splits its data across distinct documents (XPerformance for snapshots, Notas de Corretagem for trades, Informe de Rendimentos for dividends, Conta Digital Extrato for bank movements). v0.6 attacks the Conta Digital Extrato because (a) the PDF is already in hand, (b) it unlocks the TWR/MWR foundation, and (c) it has the lowest implementation cost.

## 2. Goals

- Ship **2 new MCP tools**:
  - `import_bank_extract_pdf` — parse and persist APORTE/RESGATE cash flows from XP's Conta Digital Extrato PDF
  - `get_cash_flows` — query persisted cash flows with date and kind filters, plus aggregate totals
- Add a new table `cash_flows` via schema migration v2 → v3 (idempotent, isolated, does not touch existing tables)
- Build the parser as a pure function in `src/adapters/xp/pdf-bank-extract.ts` (same pattern as `pdf-xperformance.ts`)
- Maintain the clean architecture pattern: parser (pure) + repo (DB I/O) + tool (thin wrapper)
- Maintain TDD discipline (RED → GREEN → COMMIT per task, subagent-driven execution)
- Update `ci.yml` + `release.yml` smoke tests to verify **11 tools register**
- Bump version `0.5.0` → `0.6.0` (minor: backwards-compatible schema migration + new tools)

## 3. Non-goals

- **Parsing non-investment transactions** (Pix, TED, bill payment) — out of scope; portfolio-mcp is about the portfolio, not personal finance. Lines that match the date+amount regex but do not match the investment-transfer descriptor are counted as `ignored_lines` and dropped.
- **Notas de Corretagem (trade execution notes)** — separate document, separate parser, deferred to a future iteration. Will populate the existing `transactions` table.
- **Informe de Rendimentos (annual dividend statement)** — separate document, separate parser, deferred. Will populate the existing `dividends` table.
- **Integration with `get_portfolio_summary`** — possible future addition (e.g., a `cash_flow_summary` block with YTD totals), but conceptually distinct (summary describes current state; cash flows are historical events). Defer to v0.7+.
- **TWR / MWR calculation tool** — the whole point of capturing cash flows, but a separate feature with its own design considerations (valuation snapshots, sub-period handling). Defer.
- **Backfill from CSV exports** — XP's CSV exports do not include the bank statement view. PDF only.
- **PDF batch import** — single-file imports only. If the user wants multiple periods, they import multiple times; idempotency handles overlap.
- **Mutating cash flow rows** — cash flows are immutable historical events. The tool only inserts; it never updates existing rows.


**Why a new repo (`cash-flows-repo.ts`):** consistent with the v0.5 decision to split `imports-repo.ts` out of `positions-repo.ts`. One repo per table keeps responsibilities clear and tests scoped.

**Why split `listCashFlows` and `sumCashFlows`:** the tool returns up to `limit` rows but reports `totals_brl` over **all** matching rows (ignoring limit). Two separate queries express this cleanly; combining them would either over-fetch (sum from JS array of all rows) or require window functions (more complex SQL).

## 5. Data model

### 5.1 New table `cash_flows`

```sql
CREATE TABLE IF NOT EXISTS cash_flows (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  flow_datetime  TEXT    NOT NULL,           -- ISO 'YYYY-MM-DD HH:MM:SS' (local time as printed)
  flow_date      TEXT    NOT NULL,           -- 'YYYY-MM-DD' (derived; indexed for range queries)
  kind           TEXT    NOT NULL,           -- 'APORTE' | 'RESGATE'
  amount_cents   INTEGER NOT NULL,           -- always positive; kind carries direction
  description    TEXT    NOT NULL,           -- raw line from PDF (audit trail)
  import_id      INTEGER REFERENCES imports(id),
  UNIQUE (flow_datetime, amount_cents, kind)
);

CREATE INDEX IF NOT EXISTS idx_cash_flows_date ON cash_flows(flow_date);
CREATE INDEX IF NOT EXISTS idx_cash_flows_kind ON cash_flows(kind);
```

**Design choices:**

- **`amount_cents` is always positive**; `kind` separates direction. Common convention in accounting systems; avoids "whose perspective" ambiguity (`-R$ 5.500` from the bank-account view is `+R$ 5.500` from the investment-account view).
- **UNIQUE `(flow_datetime, amount_cents, kind)`** gives idempotency. Re-importing the same PDF inserts zero new rows. A real-world collision (two transfers in the same second, identical value, identical direction) is implausible and would itself be pathological.
- **`description` excluded from UNIQUE** — included in the row for audit, but the constraint avoids tying idempotency to whitespace/casing variations of the description string.
- **`flow_date` materialized** (not a generated column or VIEW) so the index uses it directly without function evaluation. Small storage cost, big query payoff.
- **`import_id` FK** for traceability: which import produced this row.

### 5.2 Migration v2 → v3

In `src/storage/migration.ts` — same pattern as `migrateV1ToV2`, executing each DDL statement via `db.prepare(sql).run()` inside a transaction:

```ts
export function migrateV2ToV3(db: Database): void {
  const STATEMENTS = [
    `CREATE TABLE IF NOT EXISTS cash_flows (
       id             INTEGER PRIMARY KEY AUTOINCREMENT,
       flow_datetime  TEXT    NOT NULL,
       flow_date      TEXT    NOT NULL,
       kind           TEXT    NOT NULL,
       amount_cents   INTEGER NOT NULL,
       description    TEXT    NOT NULL,
       import_id      INTEGER REFERENCES imports(id),
       UNIQUE (flow_datetime, amount_cents, kind)
     )`,
    `CREATE INDEX IF NOT EXISTS idx_cash_flows_date ON cash_flows(flow_date)`,
    `CREATE INDEX IF NOT EXISTS idx_cash_flows_kind ON cash_flows(kind)`,
  ];
  const tx = db.transaction(() => {
    for (const sql of STATEMENTS) db.prepare(sql).run();
  });
  tx();
}
```

In `src/storage/schema.ts`:

- Bump `SCHEMA_VERSION` from `2` to `3`
- Append the `cash_flows` DDL to `DDL_STATEMENTS` so fresh installs get v3 directly
- Chain the migration call in `applySchema`:

  ```ts
  if (currentVersion === 1) migrateV1ToV2(db);
  if (currentVersion === 1 || currentVersion === 2) migrateV2ToV3(db);
  ```

  Fresh installs start with `currentVersion = 0`; DDL statements run idempotently via `IF NOT EXISTS`, then `SCHEMA_VERSION` is written as `3`. Conditional migration calls are no-ops on fresh installs because the DDL is already idempotent.

### 5.3 No changes to existing tables

`positions`, `transactions`, `dividends`, `imports`, `market_data_cache`, and `meta` are untouched. `imports` continues to track import metadata; new imports use `source_type = 'pdf_bank_extract'`.

## 6. Parser (`pdf-bank-extract.ts`)

### 6.1 Strategy

The PDF text extracted by `pdf-parse` collapses whitespace, producing one long string per page with rows separated by `\n`. Each transaction row has the shape:

```text
DD/MM/YY às HH:MM:SS<description><signed-amount><balance>
```

with all fields concatenated (no separators). Example (whitespace added for clarity):

```text
19/05/26 às 07:03:19  Transferência enviada para conta investimento  -R$ 5.500,00  R$ 394,33
```

A single anchored regex extracts all six capture groups per line:

```ts
const LINE_RE = /^(\d{2})\/(\d{2})\/(\d{2}) às (\d{2}:\d{2}:\d{2})(.+?)(-?R\$ [\d.,]+)(R\$ [\d.,]+)$/;
```

The greedy-min `(.+?)` for description works because the first BRL value (signed) terminates the description, and the second (always positive — balance) terminates the row.

### 6.2 Investment-transfer classification

Two regex patterns identify the relevant rows. Both are case-insensitive, tolerant of optional articles (`a`, `da`/`de`), and handle accent variations (`ê`/`e`, `ç`/`c`):

```ts
const APORTE_RE  = /transfer[êe]ncia\s+enviada\s+para\s+(?:a\s+)?conta\s+investimento/i;
const RESGATE_RE = /transfer[êe]ncia\s+recebida\s+(?:da|de)\s+(?:a\s+)?conta\s+investimento/i;
```

A line matching `APORTE_RE` becomes `kind: 'APORTE'`; matching `RESGATE_RE` becomes `kind: 'RESGATE'`. Matching neither (or both — defensive) is `ignored_lines` (counted but not persisted; both-match emits a warning).

### 6.3 Two-digit year resolution

The PDF prints `21/05/26`. The parser resolves this with the rule:

> If `YY ≤ (current_year mod 100) + 5`, treat as `20YY`. Otherwise, treat as `19YY`.

This sustains reliable parsing through roughly 2050. Document the heuristic in the parser file.

### 6.4 Metadata extraction

The PDF header carries:

```text
Conta Digital Extrato
Data da consulta: 22/05/2026 12:46:05
FELIPE CAMPELLO ... Banco XP S.A | Agência: 0001 | Conta: 16751847
Documento: 052.665.981-58
De: 23/11/2025 Até: 22/05/2026
```

The parser extracts:

- `account_holder` — name on the row above "Banco XP S.A"
- `account_number` — after `Conta:`
- `period_from` — after `De:`, converted to ISO `YYYY-MM-DD`
- `period_to` — after `Até:`, ISO

Failure to find any one field emits a warning but does not throw. `period_to` is stored as `imports.reference_date` for consistency with `import_xperformance_pdf`.

### 6.5 Page-break and footer handling

Page 2 repeats the header `DataDescriçãoValorSaldo`. The parser ignores any line that matches the header pattern only (no date). The disclaimer footer (`Extrato simples para conferência…` and the address block) does not match `LINE_RE`, so it falls through naturally as a non-match.

### 6.6 Types

```ts
export type CashFlowKind = 'APORTE' | 'RESGATE';

export interface ParsedCashFlow {
  flow_datetime: string;     // 'YYYY-MM-DD HH:MM:SS'
  flow_date: string;         // 'YYYY-MM-DD'
  kind: CashFlowKind;
  amount_cents: number;      // > 0
  description: string;       // verbatim from PDF
}

export interface ParsedBankExtractMetadata {
  account_holder: string | null;
  account_number: string | null;
  period_from: string | null;
  period_to: string | null;
}

export interface ParsedBankExtract {
  cash_flows: ParsedCashFlow[];
  total_lines: number;       // rows where LINE_RE matched (matched but maybe ignored)
  ignored_lines: number;     // matched LINE_RE but not an investment transfer
  metadata: ParsedBankExtractMetadata;
  warnings: string[];
}
```

### 6.7 Warnings catalog

| Trigger | Warning message |
| --- | --- |
| `LINE_RE` matched but neither APORTE_RE nor RESGATE_RE matched description | *(silent — counted in `ignored_lines`)* |
| Both APORTE_RE and RESGATE_RE matched description | `"Ambiguous flow direction at line {N}: {description}"` |
| `parseBRLToCents` returned `null` | `"Could not parse amount at line {N}: {raw}"` |
| Header could not extract `period_from` or `period_to` | `"Period metadata missing"` |
| Header could not extract account holder/number | `"Account metadata missing"` |
| Zero cash flows found, but text length > 0 | `"No bank extract header found — is this the right PDF?"` |

## 7. Tools

### 7.1 `import_bank_extract_pdf`

**Schema:**

```ts
export const importBankExtractPdfSchema = z.object({
  file_path: z.string().min(1).describe(
    "Absolute path to a PDF exported from XP's Conta Digital Extrato (digital account statement)."
  ),
});
```

**Handler signature:**

```ts
export async function importBankExtractPdf(
  input: ImportBankExtractPdfInput,
  deps: { db?: Database } = {},
): Promise<ImportBankExtractPdfResult>
```

**Flow:**

1. `resolve(file_path)` + `statSync` — throw if not a file
2. `parseBankExtractPdf(filePath)` → `ParsedBankExtract`
3. `createImportRecord(db, { sourceType: 'pdf_bank_extract', sourcePath: filePath, totalRows: total_lines, referenceDate: metadata.period_to })`
4. `insertCashFlows(db, parsed.cash_flows, importId)` → `{ inserted, skipped }`
5. `updateImportCounts(db, importId, { imported: inserted, updated: 0, skipped, notes })` — `notes` carries up to 10 joined warnings
6. Return result

**Result shape:**

```ts
export interface ImportBankExtractPdfResult {
  ok: true;
  import_id: number;
  source_path: string;
  period_from: string | null;
  period_to: string | null;
  total_lines: number;        // matched LINE_RE (incl. ignored)
  imported: number;           // newly inserted cash_flows
  skipped: number;            // duplicates skipped via UNIQUE constraint
  ignored_lines: number;      // matched LINE_RE but non-investment
  warnings: string[];
  preview: Array<{            // up to 10 cash flows, most recent first
    flow_date: string;
    flow_datetime: string;
    kind: CashFlowKind;
    amount_brl: number;
    description: string;
  }>;
}
```

Note: `updated: 0` always — cash flows are immutable. Re-import either inserts (new) or skips (duplicate).

### 7.2 `get_cash_flows`

**Schema:**

```ts
export const getCashFlowsSchema = z.object({
  date_from: z.string().regex(/^\d{4}-\d{2}-\d{2}$/).optional()
    .describe("ISO date YYYY-MM-DD, inclusive lower bound on flow_date."),
  date_to: z.string().regex(/^\d{4}-\d{2}-\d{2}$/).optional()
    .describe("ISO date YYYY-MM-DD, inclusive upper bound on flow_date."),
  kind: z.enum(['APORTE', 'RESGATE']).optional()
    .describe("Filter by flow direction."),
  limit: z.number().int().min(1).max(500).default(100)
    .describe("Max rows to return (default 100, max 500). Sorted by flow_datetime DESC."),
});
```

**Handler signature:**

```ts
export async function getCashFlows(
  input: GetCashFlowsInput,
  deps: { db?: Database } = {},
): Promise<GetCashFlowsResult>
```

**Flow:**

1. Build filter object from input (drop undefined)
2. `rows = listCashFlows(db, filters, limit)` — paginated, sorted DESC
3. `totals = sumCashFlows(db, filters)` — **ignores limit** so totals reflect all matches
4. Return composed result

**Result shape:**

```ts
export interface GetCashFlowsResult {
  filters: {
    date_from: string | null;
    date_to: string | null;
    kind: CashFlowKind | null;
    limit: number;
  };
  count: number;                  // rows.length
  totals_brl: {                   // over ALL matching rows, ignoring limit
    aporte_total: number;
    resgate_total: number;
    net: number;                  // aporte_total - resgate_total
  };
  rows: Array<{
    id: number;
    flow_date: string;
    flow_datetime: string;
    kind: CashFlowKind;
    amount_brl: number;
    description: string;
    import_id: number;
  }>;
}
```

**Empty-state behavior:** zero rows is a valid response. `count = 0`, `totals_brl.{aporte_total, resgate_total, net} = 0`, `rows = []`. No error.

## 8. Error handling

Tools follow the existing `throw new Error(...)` pattern. No new error taxonomy needed (the `AdvisorError` hierarchy is scoped to the advisor subsystem and not applicable here).

| Scenario | Behavior |
| --- | --- |
| `file_path` does not exist or is not a regular file | `throw new Error("Not a file: ${path}")` (matches `import_xperformance_pdf`) |
| File exists but is not a valid PDF | `pdf-parse` throws; handler propagates with original message |
| Valid PDF but wrong document type (e.g., XPerformance) | Parser returns `cash_flows: []` + warning `"No bank extract header found — is this the right PDF?"`. Tool succeeds with `imported: 0`. User sees the warning and re-tries with correct file. |
| Valid bank extract with zero investment transfers in the period | `imported: 0`, `ignored_lines: N`, no warning. Valid state (e.g., a month with no contributions) |
| Schema is at v1 or v2 | `applySchema` chains migrations to v3 — transparent to caller |
| Concurrent imports on the same file | First wins (rows inserted); second sees idempotency hits (`skipped` equals row count, `imported: 0`). Both succeed |

## 9. Testing strategy

Hybrid fixture approach — full PDF kept out of git (PII), text-extracted anonymized version committed.

| Layer | Fixture | Runs in CI? | What it verifies |
| --- | --- | --- | --- |
| Unit tests of pure helpers (`parseLine`, `isInvestmentTransfer`, `resolveAmbiguousYear`, `extractAccountMetadata`) | inline strings | Yes | 100% of parsing branches |
| Parser end-to-end at text level | `tests/fixtures/extrato-bank-sample-anon.txt` (committed; PII redacted) — `pdf-parse` stubbed to return this text | Yes | Text → cash flows pipeline |
| Parser end-to-end at PDF level | `tests/fixtures/extrato-bank-sample.pdf` (gitignored) — `it.skipIf(!existsSync(fixture))` | Skipped in CI; runs locally | PDF → text → cash flows (sanity check before release) |
| Repo (`insertCashFlows`, `listCashFlows`, `sumCashFlows`) | temp in-memory SQLite | Yes | Idempotency via UNIQUE conflict, filter combinations, totals |
| Tool handlers (`importBankExtractPdf`, `getCashFlows`) | temp DB + parser stub | Yes | Wiring, result shape, edge cases (empty result, limit semantics, totals-over-all) |
| Migration v2 → v3 | temp DB started at v2 | Yes | Idempotency (run twice without error), DDL applied, version bumped |

**Anonymized fixture creation:**

1. Run `inspect-extrato.mjs` against the real PDF, capture the text output
2. Redact: name → `FELIPE TEST`, CPF → `000.000.000-00`, agency/account → `0001 / 00000000`
3. Save to `tests/fixtures/extrato-bank-sample-anon.txt`
4. Verify the fixture preserves ≥ 3 APORTE rows and ≥ 1 RESGATE row (needed for filter and totals tests)

**`.gitignore` addition:** `tests/fixtures/*.pdf` (covers this and any future PDF fixtures).

**Expected test count addition:** ~60-80 new tests (parser ~25, repo ~12, handlers ~15, migration ~6, helpers ~12).

## 10. Backwards compatibility & risk

**Schema migration risk:** low. `cash_flows` is a new table with no dependencies on existing tables (only a FK reference to `imports(id)`, which is non-blocking). Migration is idempotent: running it on a fresh v3 install or re-running on existing v3 install is a no-op (`CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`).

**Tool count change:** smoke tests in `.github/workflows/ci.yml` and `.github/workflows/release.yml` currently grep for `9` tools. Need updates to `11`.

**README update:** add `import_bank_extract_pdf` and `get_cash_flows` entries to the Tools section; update tool-count references; add v0.6 entry to Roadmap/Changelog.

**Version bump:** `0.5.0 → 0.6.0` in `package.json`. Minor bump (new tools, additive schema, no breaking changes).

**No data migration:** no existing rows in `cash_flows` (new table). Users on v0.5 upgrade to v0.6 by `npm install` (or git pull + `npm install`) and the next process startup auto-runs `migrateV2ToV3`.
