## 1. Problem statement

`portfolio-mcp` ships v0.6 with eleven MCP tools, including four advisor primitives:

- `set_advisor_profile` / `get_advisor_profile` — risk, horizon, objective
- `calculate_allocation_drift` — gap between current vs target allocation
- `screen_assets` — rank B3 universe by criteria (FII | ACAO | ETF)
- `get_market_data` — quotes + fundamentals for specific tickers

These primitives compose into a recommendation flow, but **the LLM client must orchestrate it manually**: read profile, call drift, decide which classes are underweight, derive screening criteria from `objective`, call `screen_assets` per class, distribute BRL amounts, mark already-owned tickers. The arithmetic is mechanical and the LLM occasionally gets it wrong (especially the BRL distribution).

`suggest_buys` is the **server-side orchestrator** that performs this composition deterministically. It is the *action-tier* counterpart to `get_portfolio_summary` (the inspection-tier orchestrator from v0.5): single call in, actionable list out.

The naming reflects intent: this is a **suggestion**, not a recommendation. The DISCLAIMER from `get_market_data` is preserved verbatim (analysis is educational, not investment advice).

## 2. Goals

- Ship 1 new MCP tool: `suggest_buys`
- Compose 4 existing primitives (`profile → drift → screen → suggestions`) into a single deterministic call
- Encode the only opinionated decision (objective × asset_class → screening criteria) as a **single fixed matrix** in code, fully documented in this spec
- Output a flat suggestion list per ticker with `amount_brl`, `score`, `rationale`, `already_owned` — closed format that any MCP client can render directly
- Surface non-screenable underweight classes (TESOURO, RENDA_FIXA_PRIVADA, FUNDO) in a separate `skipped_classes` array with explicit reason — never silently drop
- Maintain clean architecture: `services/suggest-buys.ts` (pure compose) + `tools/suggest-buys.ts` (I/O wrapper) + `advisor/screening-presets.ts` (the matrix)
- Maintain TDD discipline (RED → GREEN → COMMIT per task)
- Update CI smoke tests to verify 12 tools register
- Bump version `0.6.0` → `0.7.0` (minor — new tool, no breaking change)

## 3. Non-goals

- **No new market-data source.** Only what `screen_assets` already exposes (brapi quote + fundamentals).
- **No LLM-side ranking.** The orchestrator returns a closed top-N list per class. Clients that want broader candidate pools can call `screen_assets` directly.
- **No suggestions for non-screenable classes.** TESOURO / RENDA_FIXA_PRIVADA / FUNDO are surfaced in `skipped_classes` with the underweight gap; the user allocates manually.
- **No rebalance SELL recommendations.** Drift report's SELL actions are out of scope; this tool only suggests BUYs against underweight classes. Selling overweight positions is a separate decision tree (tax, liquidity, intent).
- **No customization of the matrix via profile or input.** Single fixed mapping. Customization is a deferred TODO if the heuristic proves too rigid in practice.
- **No portfolio-size constraints.** Suggestions ignore minimum-lot logic (FIIs trade in lots of 1, ACAOs sometimes in 100). The user's broker UI enforces this.

## 4. Architecture

### High-level

```text
┌──────────────────────────────────────────────────────────────┐
│ tools/suggest-buys.ts            (I/O wrapper, ~50 LOC)      │
│   - requireOutboundEnabled()  ─► AdvisorProfile              │
│   - getDb() + listPositions() ─► PositionRow[]               │
│   - calculateAllocationDrift(target_path) ─► DriftReport     │

└──────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────┐
│ services/suggest-buys.ts        (pure, ~120 LOC)             │
│   - composeSuggestions(                                      │
│        drift: DriftReport,                                   │
│        screenResultsByClass: Map<UniverseClass, ScreenResult>│
│        ownedTickers: Set<string>,                            │
│        top_n: number,                                        │
│     ): SuggestBuysResult                                     │
└──────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────┐
│ advisor/screening-presets.ts    (the matrix, ~40 LOC)        │
│   - criteriaFor(                                             │
│        objective: 'income'|'growth'|'balanced',              │
│        cls: 'FII'|'ACAO'|'ETF',                              │
│        top_n: number,                                        │
│     ): ScreenCriteria                                        │
└──────────────────────────────────────────────────────────────┘
```

### Why split this way

- **`screening-presets.ts`** isolates the only opinionated decision. Changing the matrix later is a one-file edit with focused tests.
- **`services/suggest-buys.ts`** is the pure compose layer — no `screen_assets` calls, no DB, no fs. Takes already-fetched screen results plus owned tickers and produces the output. Trivial to unit-test with synthetic inputs.
- **`tools/suggest-buys.ts`** is the I/O orchestration: loads profile, queries DB, calls `screen_assets` per class. Thin enough that integration tests against real brapi (or a fake source) cover it end-to-end.

This mirrors the v0.5 split (`services/portfolio-summary.ts` pure + `tools/get-portfolio-summary.ts` wrapper).

## 6. Output shape

### TypeScript interface

```ts
export type ScreenableClass = 'FII' | 'ACAO' | 'ETF';
export type NonScreenableClass = 'TESOURO' | 'RENDA_FIXA_PRIVADA' | 'FUNDO';

export interface BuySuggestion {
  asset_class: ScreenableClass;
  ticker: string;
  amount_brl: number;          // = class_gap_brl / top_n, rounded to 2dp
  score: number;               // forwarded from ScreenResult.score (0..1)
  rationale: string;           // forwarded from ScreenResult.why (e.g. "DY 9.8% (median 7.1%)")
  already_owned: boolean;      // true if listPositions() contains this ticker
}

export interface SkippedClass {
  asset_class: NonScreenableClass;
  underweight_brl: number;     // = drift.action.amount_brl
  reason: string;              // fixed text "screening não cobre <CLASS>; alocar manualmente."
}

export interface SuggestBuysResult {
  ok: true;
  total_to_invest_brl: number; // sum of suggestion.amount_brl (excludes skipped_classes)
  total_skipped_brl: number;   // sum of skipped_class.underweight_brl
  suggestions: BuySuggestion[];
  skipped_classes: SkippedClass[];
  warnings: string[];          // includes DISCLAIMER + per-class screening warnings
}
```

### Example output (realistic)

### Design decisions explicit in this shape

- `suggestions` is **flat** (not grouped by class). Sort order: same order as drift report (largest |drift_pp| first), then by score desc within each class. Clients that want per-class grouping can group on `asset_class`.
- `total_to_invest_brl` excludes skipped classes (you can't act on them in this tool). `total_skipped_brl` is reported separately so the sum `total_to_invest + total_skipped` equals the full underweight gap the user would close with manual decisions.
- `already_owned` is a forward signal to the client UI — *not* a filter. Both new and existing tickers can appear.
- `rationale` is the verbatim `ScreenResult.why` from screening — already includes the comparison vs median. No extra wording added.

## 7. The matrix: `objective × asset_class → ScreenCriteria`

This is the **single opinionated decision** in this feature. Spec-locked so changes go through a doc + tests update, not a quiet edit.

### Module shape (`advisor/screening-presets.ts`)

```ts
import type { ScreenCriteria } from "./screening.js";
import type { UniverseClass } from "./market-data/source.js";
import type { AdvisorProfile } from "./profile.js";

export function criteriaFor(
  objective: AdvisorProfile['objective'],
  cls: UniverseClass,
  top_n: number,
): ScreenCriteria;
```

### Matrix

| objective × class | sort_by | order | filters |
| --- | --- | --- | --- |
| **income × FII** | `dividend_yield` | desc | `min_dividend_yield_pct: 6`, `max_pvp: 1.5`, `max_vacancy_pct: 15`, `min_market_cap_brl: 200_000_000` |
| **income × ACAO** | `dividend_yield` | desc | `min_dividend_yield_pct: 4`, `min_market_cap_brl: 1_000_000_000` |
| **income × ETF** | `dividend_yield` | desc | `min_dividend_yield_pct: 3`, `min_market_cap_brl: 100_000_000` |
| **growth × FII** | `market_cap` | desc | `min_market_cap_brl: 500_000_000`, `max_pvp: 1.2` |
| **growth × ACAO** | `roe` | desc | `min_roe_pct: 10`, `min_market_cap_brl: 1_000_000_000` |
| **growth × ETF** | `price_change_30d` | desc | `min_market_cap_brl: 500_000_000` |
| **balanced × FII** | `dividend_yield` | desc | `min_dividend_yield_pct: 4`, `max_pvp: 1.3`, `min_market_cap_brl: 300_000_000` |
| **balanced × ACAO** | `roe` | desc | `min_roe_pct: 5`, `min_market_cap_brl: 500_000_000`, `min_dividend_yield_pct: 2` |
| **balanced × ETF** | `market_cap` | desc | `min_market_cap_brl: 500_000_000` |

### Rationale per cell

- **income**: prioritises cash distributions. Higher `min_dy` thresholds, lower allowed P/VP (more conservative entry price). FII filters add `max_vacancy_pct` because vacancy directly threatens distributions.
- **growth**: prioritises capital appreciation. ACAO uses ROE (operating efficiency), ETF uses 30d momentum (proxy for trend strength), FII uses market cap (larger = more stable and tracks the index closer).
- **balanced**: requires both income floor (`min_dy ≥ 2-4`) and growth floor (`min_roe ≥ 5` on ACAO). Defaults to DY-sort on FII (cash flow bias for B3 income asset class) and ROE-sort on ACAO (efficiency proxy).

### Limit handling

`limit` in the returned criteria is always `top_n` (forwarded verbatim). This is what controls how many suggestions surface per class.

### Excluded tickers

`exclude_tickers` in `screenAssets` input is left empty in the criteria from this module — the orchestrator merges `profile.excluded_tickers` into the `screenAssets` call directly (already supported by that tool).

## 8. Mapping drift classes to screen calls

```ts
// In tools/suggest-buys.ts
const SCREENABLE: ScreenableClass[] = ['FII', 'ACAO', 'ETF'];

for (const driftRow of drift.drift) {
  if (driftRow.status !== 'underweight') continue;          // ok or overweight: skip
  if (driftRow.action == null || driftRow.action.side !== 'BUY') continue;
  if (!SCREENABLE.includes(driftRow.asset_class)) {
    skippedClasses.push({
      asset_class: driftRow.asset_class,
      underweight_brl: driftRow.action.amount_brl,
      reason: `screening não cobre ${driftRow.asset_class}; alocar manualmente.`,
    });
    continue;
  }
  const criteria = criteriaFor(profile.objective, driftRow.asset_class, input.top_n);
  const screen = await screenAssets({
    asset_class: driftRow.asset_class,
    criteria,
    exclude_tickers: [],   // profile exclusions applied inside screenAssets
  });
  // …compose suggestions for this class, with amount_brl = action.amount_brl / actual_returned
}
```

Notes:

- `screen_assets` already merges `profile.excluded_tickers` and `profile.excluded_classes`. No double-handling needed here.
- If a class is fully excluded via `profile.excluded_classes`, `screen_assets` returns empty results; the orchestrator emits a warning and skips that class (no suggestion, no skipped_class entry — the user opted out).

## 9. amount_brl distribution

For each screenable underweight class with `actual_returned` results from `screenAssets`:

```text
amount_per_ticker = round2(class_action.amount_brl / actual_returned)
```

Where:

- `class_action.amount_brl` = the drift report's `action.amount_brl` for that class (already in BRL, full gap to close).
- `actual_returned` = `screen.returned` (may be < `top_n` if the universe is small or filters too strict).

If `actual_returned === 0`, emit a warning `"<CLASS> underweight but no tickers passed screening (universe=N, filtered=M); relax filters or screen manually"` and contribute nothing to `total_to_invest_brl`.

`round2` is the existing helper from `services/money.ts`. Rounding errors are absorbed silently — `total_to_invest_brl` is recomputed by summing `amount_brl` post-rounding (not from the unrounded total), so the displayed total always equals the sum of displayed line items.

## 10. Edge cases & warnings

| Scenario | Handling |
| --- | --- |
| Profile missing | `ProfileMissingError` propagates (from `requireOutboundEnabled`) |
| `outbound_enabled=false` | `OutboundDisabledError` propagates (same source) |
| Disclaimer not accepted | `DisclaimerRequiredError` propagates |
| No positions in DB | Drift returns empty → `suggestions=[]`, `skipped_classes=[]`, warning `"No positions; import data first"` (from `computeDrift`, forwarded) |
| `~/.xp-mcp/allocation.json` missing | `computeDrift` throws — propagate as-is (user must configure target first) |
| All classes within tolerance | `suggestions=[]`, `skipped_classes=[]`, `total_to_invest_brl=0`. Warning: `"Portfolio is within tolerance for all classes; no buys suggested."` |
| Only non-screenable classes underweight | `suggestions=[]`, `skipped_classes` populated, `total_to_invest_brl=0`, `total_skipped_brl>0`. No special warning beyond the skipped entries themselves. |
| `screen_assets` returns 0 results for a class | Warning `"<CLASS> underweight by X BRL but no tickers passed screening (universe=N, filtered=M)"`, no suggestions for that class, no skipped_class entry (it's a different failure mode than non-screenable). `class_action.amount_brl` not added to either total. |
| Per-ticker brapi error inside screen | Already absorbed inside `screen_assets.warnings` — forward those warnings verbatim with class prefix |
| `top_n` higher than universe size | `screen.returned < top_n` → divide by `actual_returned` not `top_n`. Already covered in §9. |
| Profile excludes the underweight class via `excluded_classes` | `screen_assets` returns empty + own warning. Forward that warning. Class contributes 0 to `total_to_invest_brl` and is NOT in `skipped_classes` (user opted out, not a tooling limitation). |

DISCLAIMER is always present as the first entry in `warnings`. Other warnings appended after.

## 11. Sub-function contracts

### `criteriaFor(objective, cls, top_n): ScreenCriteria`

Pure. Returns the exact `ScreenCriteria` per the matrix. Throws if `cls` not in `{FII,ACAO,ETF}` (caller responsibility to filter).

### `composeSuggestions(drift, screenResultsByClass, ownedTickers, top_n): SuggestBuysResult`

Pure. Takes:

- `drift: DriftReport`
- `screenResultsByClass: Map<ScreenableClass, ScreenAssetsResult>` — null entries mean class skipped due to non-screenable; missing entries mean the class wasn't underweight.
- `ownedTickers: Set<string>` — from `listPositions()`
- `top_n: number`

Returns the full `SuggestBuysResult`. No I/O. All warnings from input screens are merged.

### `suggestBuys(input, deps?): Promise<SuggestBuysResult>`

The I/O wrapper. `deps` allows injecting `source: MarketDataSource` for tests (mirroring `screen_assets` pattern). DB and profile loaders use the standard global helpers.

## 12. Testing strategy

### Unit tests — `services/suggest-buys.test.ts`

Cover `composeSuggestions` directly with synthetic `DriftReport` + `ScreenAssetsResult` fixtures. ~10-12 tests:

- Single underweight screenable class with full screening result
- Multiple underweight screenable classes
- Non-screenable underweight class → goes to skipped_classes
- Mixed screenable + non-screenable
- `already_owned` correctly flagged from `ownedTickers` set
- `actual_returned < top_n` → amount_brl divides by `actual_returned`
- `actual_returned === 0` → warning, no suggestion, no totals
- All classes within tolerance → empty output + warning
- DISCLAIMER always present as first warning
- `total_to_invest_brl` equals sum of suggestion amount_brl (post-round)
- `total_skipped_brl` equals sum of skipped underweight amounts
- Drift with no positions → empty output, forwarded warning

### Unit tests — `advisor/screening-presets.test.ts`

Cover `criteriaFor` matrix. ~10 tests:

- Each (objective, class) combination produces the expected criteria
- `top_n` forwards to `limit` verbatim
- Same input → same output (pure)
- Throws on invalid class

### Integration test — `tools/suggest-buys.test.ts`

End-to-end with **mocked `MarketDataSource`** (no live brapi):

- Stubs profile (`outbound_enabled=true`, `objective='income'`)
- Seeds DB with positions producing known drift (FII underweight)
- Stubs `MarketDataSource.listUniverse('FII')` + `getQuote`/`getFundamentals` for ~5 tickers
- Asserts: 3 suggestions returned (top_n default), correct `amount_brl` distribution, `already_owned` set correctly, DISCLAIMER in warnings, `outbound_enabled=false` triggers error
- Asserts: missing allocation target → error propagates with helpful message

Estimated tests added: ~25 (15 unit `composeSuggestions` + presets + 10 integration).

## 14. Out of scope for this spec (deferred TODOs)

- Customisable matrix (via profile field or input override). Deferred until evidence the fixed matrix is too rigid.
- Backtest harness ("would suggest_buys output X have outperformed?"). Whole separate feature.
- Suggestions for non-screenable classes (TESOURO via Tesouro Direto API, RF via curated list). Requires new data sources.
- SELL recommendations for overweight classes. Different decision tree (tax/cost basis/liquidity).
- Lot-size awareness (round to whole shares/cotas). Broker UI enforces; out of scope.
- Per-call override of `objective` (caller wants to suggest as if income-oriented without changing profile). YAGNI.
