## 1. Problem statement

`xp-mcp` v0.2.0 ships a working MCP server with a real feature killer (`calculate_allocation_drift`), a polished README, MIT license, and green CI. The repository is public on GitHub.

But the **adoption friction is still ~10 minutes** for a new user:

1. `git clone` the repo
2. `npm install` (downloads ~50MB of `node_modules`)
3. `npm run build` (compiles TypeScript)
4. Locate the absolute path of `dist/index.js`
5. Edit `claude_desktop_config.json` with that absolute path
6. Restart Claude Desktop

Anyone who isn't already a TypeScript developer will bounce at step 1. Even developers will bounce if "I'll just try this quickly" turns into a 10-minute setup.

The single highest-leverage change to fix this is **publishing the server to npm** so users can replace all 6 steps above with one config snippet:

```json
{ "command": "npx", "args": ["-y", "xp-investimentos-mcp"] }
```

`npx` then handles download, cache, and execution transparently. Setup drops from ~10 min to ~30 sec.

Along with the npm publish, two listing actions amplify discoverability with marginal effort:

- **Smithery.ai listing** — curated MCP directory, used by many Claude-adjacent clients
- **PR to `punkpeye/awesome-mcp-servers`** — 87k-star community catalog, primary discovery surface for MCP server hunters

This spec defines v0.3.0 as the **distribution release**: same code, same tools, ~20× lower adoption friction.

## 2. Goals

- Publish `xp-investimentos-mcp@0.3.0` to the public npm registry
- Automate future releases through GitHub Actions triggered by `v*` tags
- Configure npm provenance so the registry shows "Built and signed by GitHub Actions" — applies to releases published via the workflow (v0.3.1+); the first manual publish of v0.3.0 will not have provenance (see §6.3 and Decision #10)
- Ship `smithery.yaml` configured for stdio/local mode and open PR to Smithery
- Open PR adding the project to `punkpeye/awesome-mcp-servers`
- Update README so the Quick Start is the `npx`-based one-snippet config
- Preserve clone+build instructions for contributors (moved to a Development section)

## 3. Non-goals

- Version 1.0.0 — project is still iterating; semver stays in `0.x.y` (signal of "API may change")
- Renaming the GitHub repo (`github.com/Satsuj1n/xp-mcp` stays; only the npm package name differs)
- Adding new MCP tools, new parsers, or any runtime behavior change
- DB schema changes
- Multi-language documentation (README stays English-only)
- Submitting PRs to `modelcontextprotocol/servers` (official Anthropic repo — historically rejects third-party servers); to `appcypher/awesome-mcp-servers` or `wong2/awesome-mcp-servers` (lower ROI per pergunta 4 of brainstorming)
- Smithery hosted-mode support (forbidden by design — server reads `~/.xp-mcp/data.db` on the user's machine)
- Custom `CHANGELOG.md` (GitHub auto-generated release notes are sufficient)
- Promotion outside the canonical channels listed above (no Twitter blast, no blog post — those can happen post-release as separate chores)

## 4. Decisions log

Resolved during brainstorming. Recorded here so the implementation plan and future readers see *why*, not just *what*.

| # | Question | Decision | Rationale |
|---|---|---|---|
| 1 | Release scope: ship the 3 components together or split? | **All three together (option A)** — package.json + workflow + smithery.yaml + README updates land in the same v0.3.0 release | User-facing definition of "v0.3 = distribution" matches the original roadmap. Splitting would create v0.3, v0.3.1, v0.3.2 with no real signal between them. |
| 2 | npm package name — `xp-mcp` (unscoped, original) vs scoped vs descriptive alternative | **`xp-investimentos-mcp`** (unscoped, descriptive) | `xp-mcp` is **already taken** in the registry by an unrelated 2025 package with 8 versions. `xp-investimentos-mcp` is unambiguous (no "Windows XP" confusion), maximizes SEO ("xp investimentos" is the broker's actual name), and stays unscoped for discoverability. |
| 3 | Publish strategy — manual local vs CI-automated | **Automated via GitHub Actions** on tag push (`tags: ['v*']`) using `NPM_TOKEN` secret | One-time 20-min investment in the workflow saves ~5 min per future release and eliminates the entire "I forgot to build before publishing" class of bug. Provenance attestation is free once we're in CI. |
| 4 | awesome-mcp catalogs — which repo(s) to target | **Only `punkpeye/awesome-mcp-servers`** (87k stars) | Highest-ROI single target. `modelcontextprotocol/servers` (86k) is the official Anthropic repo and effectively only lists their own reference servers — third-party PRs are usually closed. The other two community forks (`appcypher` 5.5k, `wong2` 4k) get ~6% of `punkpeye`'s traffic and can be opportunistic chores later, not v0.3 scope. |
| 5 | Smithery hosted vs local mode | **Local mode** (Smithery lists; Claude Desktop runs via `npx`) | Hosted is incompatible with the architecture — server reads `~/.xp-mcp/data.db` on the user's machine. Each user needs their own local instance. |
| 6 | `bin` field — single name or alias for short usage? | **Single `bin: xp-investimentos-mcp`** (no `xp-mcp` alias) | A `xp-mcp` alias would collide with the existing `xp-mcp@1.0.7` squat package if the user globally installs both. One canonical name avoids ambiguity. |
| 7 | Use `private: true → false` or remove the field? | **Remove `"private"` entirely** | npm's default is "public" — `private` only exists as a publish-blocking flag. Removing it is more semantic than setting it to `false`. |
| 8 | Trigger event for the release workflow | **`tags: ['v*']`** (not `release: published`) | Tag → publish → release in this order makes npm the source of truth for the version. If someone deletes a tag accidentally, the npm package is already locked. |
| 9 | npm provenance — opt in? | **Yes (`--provenance --access public`)** in the release workflow. **First manual publish of v0.3.0 is non-provenance** (provenance requires OIDC from GitHub Actions environment, not available locally). From v0.3.1 onward, every workflow-published release carries provenance. | Free SLSA attestation for all but the bootstrap release. Shows "Built and signed by GitHub Actions from <commit> via <workflow>" on the npm package page. Audit trail at zero cost once bootstrapped. |
| 10 | First publish — manual or via workflow? | **Manual local publish for `0.3.0`** (one time only); subsequent releases via workflow | Granular automation token can be scoped to the package, but the package doesn't exist until first publish. Manual one-time bootstrap is simpler than a temporary wider-scoped token. |
| 11 | Node version in release workflow | **Node 22 (single version)** | Release uses the newest LTS for deterministic compilation. The existing `ci.yml` keeps Node 20 + 22 matrix for compatibility testing — separation of concerns. |
| 12 | GitHub Release notes | **Auto-generated via `softprops/action-gh-release` with `generate_release_notes: true`** | No manual `CHANGELOG.md` maintenance. GitHub assembles changelog from PR/commit titles since last tag. |
| 13 | Definition of Done — include external PR merges? | **No** — DoD covers items under the author's control (1-8); external PR merges (9-10) are observability targets, not release gates | A solo-maintained project can't have its release gated by an unrelated maintainer's review schedule. Tag and npm package are deterministic; external listings are best-effort. |

## 5. Architecture overview

Three semi-independent sub-components, sharing the v0.3.0 tag:

```text
v0.3.0 release
├── (1) npm publish artifact   →  package.json + release.yml + first publish
├── (2) Smithery listing PR    →  smithery.yaml + PR to smithery-ai/smithery
└── (3) awesome-mcp PR          →  PR to punkpeye/awesome-mcp-servers
```

**Dependencies**: (2) and (3) reference the published npm package, so both block on (1) succeeding. (2) and (3) are independent of each other and can be opened in parallel.

**Boundaries**:

- (1) is **fully internal** — files in this repo, one external service (npm registry) under credential control
- (2) and (3) are **inbound to external repos** — submit PRs, wait for review, no further code from us
- The DoD treats (1) as blocking and (2), (3) as completion criteria that don't block tag

```diff
+    "model-context-protocol",
+    "claude",
+    "claude-desktop",

   "type": "module",
   "bin": {
-    "xp-mcp": "./dist/index.js"
+    "xp-investimentos-mcp": "./dist/index.js"
   },
+  "files": ["dist", "README.md", "LICENSE"],
   "scripts": {
     "build": "tsc",
+    "prepublishOnly": "npm run typecheck && npm run build",
     "start": "node dist/index.js",
     "dev": "tsx src/index.ts",
     "typecheck": "tsc --noEmit",
     "test": "node --test --import tsx 'src/**/*.test.ts'"
   },
   "engines": { "node": ">=20" }
}
```

**Field-by-field rationale**:

- **`name`**: changed per decision #2
- **`version`**: bump from 0.2.0 → 0.3.0
- **`private` removed**: npm default is public; field only exists to block (decision #7)
- **`license`, `author`, `repository`, `homepage`, `bugs`**: standard discoverability metadata. npm renders these on the package page
- **`keywords`**: bilingual (PT brand "xp-investimentos" + EN umbrella terms). Cost of including too many is zero; cost of missing one is invisibility
- **`bin`**: renamed to match package name (decision #6)
- **`files`**: whitelist — without it, `npm publish` ships `src/`, `docs/`, `.github/`, etc. Tarball stays minimal and contents are predictable
- **`prepublishOnly`**: runs on `npm publish` only (not on `npm install`). Guarantees the dist tarball is freshly built and typechecks

### 6.2 Release workflow — `.github/workflows/release.yml`

```yaml
name: Release

on:
  push:
    tags: ['v*']

permissions:
  contents: write   # create GitHub Release
  id-token: write   # OIDC for npm provenance

jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          registry-url: 'https://registry.npmjs.org'
          cache: npm
      - run: npm ci
      - run: npm run typecheck
      - run: npm run build
      - name: Smoke test MCP server
        run: |
          OUTPUT=$(node dist/index.js <<'EOF'
          {"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"release-ci","version":"0.0.0"}}}
          {"jsonrpc":"2.0","method":"notifications/initialized"}
          {"jsonrpc":"2.0","id":2,"method":"tools/list"}
          EOF
          )
          echo "$OUTPUT" | grep -q '"name":"get_positions"' || { echo "Smoke test failed"; exit 1; }
          echo "$OUTPUT" | grep -q '"name":"calculate_allocation_drift"' || { echo "Smoke test failed"; exit 1; }
      - run: npm publish --provenance --access public
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
      - uses: softprops/action-gh-release@v2
        with:
          generate_release_notes: true
```

**Workflow rationale**:

- **Trigger `tags: ['v*']`**: tag → publish → release order keeps npm as source of truth (decision #8)
- **`id-token: write`**: enables OIDC trust between GitHub and npm for provenance (decision #9)
- **`registry-url`**: forces npm CLI to point at the public registry (avoids accidental publish to a private registry if one is configured)
- **Smoke test inline**: reuses the same `initialize → tools/list` smoke from `ci.yml` and grep-asserts the expected tools. Defense in depth — if `dist/` is broken, we don't publish
- **`--provenance --access public`**: provenance requires `--access public` to be explicit (npm default for unscoped is public, but the flag is required to satisfy OIDC)
- **`softprops/action-gh-release`**: creates the GitHub Release from the tag with auto-generated notes (decision #12)

### 6.3 npm operational setup (one-time)

1. Create an npm account at `npmjs.com/signup` if not present
2. Generate a **Granular Access Token** at `npmjs.com/settings/<user>/tokens/new`:
   - Type: `Automation` (no 2FA prompt — appropriate for CI)
   - Packages: `xp-investimentos-mcp` (after first publish — see step 4)
   - Permissions: `Read and write`
3. Add the token as repository secret `NPM_TOKEN` at `github.com/Satsuj1n/xp-mcp/settings/secrets/actions`
4. **First publish (manual, local, one time)**:

   ```sh
   npm whoami    # verify logged in
   npm publish --access public
   ```

   **Note**: no `--provenance` flag on this manual publish — provenance requires the OIDC token available only inside GitHub Actions runners. The workflow handles `--provenance` for all subsequent releases (v0.3.1+). Once the package exists in the registry, the granular token from step 2 can be scoped to it.

## 7. Component 2 — Smithery listing

### 7.1 `smithery.yaml` (repo root)

```yaml
# Smithery configuration — see https://smithery.ai/docs/config
startCommand:
  type: stdio
  command: npx
  args:
    - "-y"
    - xp-investimentos-mcp
  # No configSchema: server reads ~/.xp-mcp/* on its own;
  # all tool inputs (file_path, target_path) come per-call,
  # not via process startup.
```

**Rationale**:

- **`type: stdio`** matches the actual transport (decision #5)
- **`npx -y`** is the canonical reproducible invocation across any user machine
- **No `configSchema`** because xp-mcp has no startup-time configuration (no env vars, no flags)
- **References the published npm package name** — Smithery YAML must reference real, public artifacts

### 7.2 Smithery PR

After the npm package is live and `smithery.yaml` is committed:

1. Visit `https://smithery.ai/new` (or the equivalent submission flow at the time of release)
2. Provide repo URL: `https://github.com/Satsuj1n/xp-mcp`
3. Provide npm package name: `xp-investimentos-mcp`
4. Wait for Smithery curators to review

This is a submission, not a self-merge — Smithery's curators decide acceptance and timing. No control over merge ETA.

## 10. Execution sequence

Strict order — each step gates the next.

| # | Step | Side-effects | Reversible? |
|---|---|---|---|
| 1 | Create branch `feat/v0.3-npm-publish`; commit `package.json`, `release.yml`, `smithery.yaml`, README updates | Repo branch only | Yes (delete branch) |
| 2 | `npm pack` locally; inspect tarball contents (`tar tzf *.tgz`); confirm only `dist/`, `README.md`, `LICENSE` ship | None (pack is local) | N/A |
| 3 | Run `npm run prepublishOnly` to confirm typecheck + build chain works | None (script only) | N/A |
| 4 | Open PR for the branch; wait for `ci.yml` green | None | Yes |
| 5 | Merge PR to main | Main moves forward | Reverts possible |
| 6 | One-time: create npm account if absent, log in (`npm login`), confirm `npm whoami` | npm account state | Yes (delete account, not recommended) |
| 7 | **First manual publish**: `npm publish --access public` from main checkout (no `--provenance` — local env can't generate OIDC attestation) | **Package locked at v0.3.0 in registry forever** | **No** (deprecate possible, unpublish only within 24h with restrictions) |
| 8 | Create granular automation token scoped to `xp-investimentos-mcp`, add to GitHub Secrets as `NPM_TOKEN` | Token exists | Yes (revoke) |
| 9 | Tag locally: `git tag v0.3.0 && git push --tags` | Triggers `release.yml`; second publish attempted via workflow | Tag deletable but **registry already has v0.3.0 from step 7** — workflow's republish will fail (npm rejects duplicate versions) |
| 10 | **Skip the workflow for v0.3.0** (already published in step 7). Validate workflow with v0.3.1 as a no-op patch bump, **OR** publish v0.3.0 directly through the workflow and skip step 7 | See below | See below |

**Step 7 vs 9 conflict — resolution**: the first publish creates a chicken-and-egg with the scoped token. Two valid resolutions:

- **Resolution A** (preferred): publish v0.3.0 manually (step 7), then create the token for future releases. Workflow first runs on v0.3.1 or later. Pro: simplest token scoping. Con: workflow remains untested until the next patch release.
- **Resolution B**: create a *wider* automation token (account-scoped, not package-scoped), use it to publish v0.3.0 via the workflow, then revoke the wide token and create a package-scoped one for future use. Pro: workflow is exercised on the first release. Con: brief existence of a wider token.

**Decision: Resolution A.** Reasoning: the workflow itself was inspected manually and matches the proven `ci.yml` smoke test. A no-op patch bump (v0.3.1 with only a tiny doc tweak) within a few days of v0.3.0 acts as the workflow's smoke test under realistic conditions. Less risk surface than passing wide tokens through CI.

## 12. Rollback / safety net

| Scenario | Mitigation |
|---|---|
| Workflow (or manual publish) ships a broken dist that passes smoke but fails on real use | `npm deprecate xp-investimentos-mcp@0.3.0 "broken — please use 0.3.1"` — does **not** unpublish; existing installs keep working but new installs see warning. Then fix and ship 0.3.1. |
| Wrong package name typo'd in publish (`xp-invesimentos-mcp`) | Same: deprecate the typo'd package, publish correct name. The `npm pack` local check in step 2 of §10 exists specifically to catch this *before* publish. |
| `NPM_TOKEN` exposed in logs or committed | Revoke immediately at `npmjs.com/settings/<user>/tokens`, generate replacement, update GitHub Secrets. |
| `smithery.yaml` syntactically invalid | PR-only flow — Smithery curators reject, no automatic publication. Iterate the YAML and resubmit. |
| `awesome-mcp` PR formatting wrong | Maintainer comments asking for fix — iterate the PR. No public artifact damaged. |

`npm unpublish` is intentionally **not** in the toolbox. npm's policy: unpublish only allowed within 72 hours of publish and only if no downstream package depends on the version. Deprecate is the community-accepted approach.
